# Postman regressietests

One collection per feature, generated from a scenario file in the repo. The same collection runs locally (Postman app
or CLI) and on Test (GitHub). `postman/features/bankrekeningnummers/scenarios.js` is the reference implementation:
when in doubt, do what it does.

## 1. Architecture

**The Postman workspace is the source of truth.** Not everyone who works on the tests has the repo, so existing
collections are maintained in the Postman app and GitHub runs them from the workspace. The scenario files and
`generate.js` are only used to create the first version of a new feature's collection, which is then imported in the
workspace. Generated collection files are not committed (a daily sync from Postman to the repo for version control is
planned).

```
postman/
  shared/
    root-prerequest.js      token, VR-Initiator, VR-Api-Version, funcs (one source for every collection)
    helpers.js              test-script helpers: RETRY/retryIf, HELPERS (matches, getCI, resolve, norm)
    builders.js             request builders + endpoint checks (registreer, wachtOp, beheerDetail, historiek, ...)
  features/<feature>/
    scenarios.js            ONLY data: the scenarios of this feature
  generate.js               node postman/generate.js [feature]  ->  postman/collections/<feature>.postman_collection.json
  collections/              generated, not committed (import in the Postman workspace)
.github/workflows/
  postman-feature.yml       one feature: dropdown (workflow_dispatch) or reusable (workflow_call), input: feature
  regressie-all.yml         matrix over all features -> postman-feature.yml
```

- A feature file contains **data, not scripts**. Scripts are generated by the builders. If a scenario needs a check
  the builders can't express, extend the builders (generically), don't inline a one-off script.
- Every collection gets the same root pre-request script from `shared/root-prerequest.js`.
- The environments (`Local`, `Test`) live only in the Postman workspace, not in the repo.

## 2. Variables

| Kind | Where | Examples |
|---|---|---|
| Configuration | Postman environment (`Local`, `Test`) | `beheer_url`, `publiek_url`, `acm_url`, `token_url`, `maxRetries`, `retryDelayMs`, `kboModus`, `superAdmin` |
| Secrets | Postman Vault (`{{vault:test_clientSecret}}`), `--env-var` in GitHub. Local uses the committed docker-compose dev client directly. The publiek API key is always read from the vault secret `vr-api-key` (`--env-var "vr-api-key=..."` in GitHub) | `clientId`, `clientSecret`, `vr-api-key` |
| Fixed reference data that must exist on that environment | Postman environment, prefix `testdata_` | `testdata_ipdcProductNummer`, `testdata_kboNummer` |
| Runtime state | collection variables, set by scripts | `vCodeA`, `vCodeD`, `sequence`, `naamX`, `token`, `publiekApiKey`, `ibanA`, `inszFrodo` |

Rules:
- **If a script `set`s it, it never exists in an environment.** An environment variable wins over a collection
  variable when `{{x}}` is resolved, so a stale `vCodeA` or `sequence` in the environment silently breaks the run.
- Scripts use `pm.collectionVariables` for state. Never `pm.environment.set`.
- `testdata_*` is read-only: a test may reference it, never change it (parallel runs share it).
- Tests never branch on the environment name. Differences between local and Test are explicit settings
  (`kboModus: 'random' | 'bestaand'`, `superAdmin: true | false`, `testdata_ipdcProductNummer`, ...).
- Values specific to one scenario that must survive a retry get the scenario id in the key
  (`bevestigingsToken_<ID>_<rol>`, `naam_<ID>_<rol>`).

## 3. Scenario rules

1. **Self-contained.** A scenario registers every vereniging it needs (roles `A`, `D`, `X`, `Y`, `K`...) and stores
   the vCodes in `vCode<rol>`. It never depends on another folder or on existing data (except read-only `testdata_*`).
   Folders can run in any order and in parallel.
2. **Unique data.** Namen contain the scenario id and a `{{$randomUUID}}`. IBANs are generated (valid Belgian IBAN).
   INSZ/KBO only where the API requires known numbers: then from `testdata_*` or the root script lists.
3. **Fictional persons:** Lord of the Rings names (Frodo Baggins, Samwise Gamgee, Aragorn Elessar, ...).
4. **Assert only on your own data.** Filter zoek results on your own vCode (`q=vCode:{{vCodeA}}`). Never count
   global results or assume "the latest" vereniging.
5. **One rule per scenario.** The name states the rule and the outcome: `Zelfde IBAN met spaties -> gededupliceerd`.
   Cover per rule: the happy path, every reason for rejection/niet-overnemen, boundaries (same day, open start/end,
   case/format differences), and "nothing to do" (no event).
6. **Check every endpoint where the data is visible**, with the projection-specific shape:
   beheer detail (with ids), historiek (gebeurtenis + data), beheer zoeken, publiek detail, publiek zoeken
   (no ids, no persoonsgegevens). Only generate requests for endpoints where the group is visible.
7. **Persoonsgegevens.** Where relevant, assert that INSZ/IBAN/titularissen do *not* appear where they must not
   (publiek endpoints, historiek of niet-overgenomen items). Use a "niet in response" check on the resolved value.
8. **Validation errors (400)** get their own scenarios: expected status + the problem details message
   (`pm.response.json().errors` / `detail`), not just the status.

## 4. Consistency and retries

Retry limits come from the environment (`maxRetries`, `retryDelayMs`); the root script waits when `loopCounter > 0`.

| Situation | Pattern |
|---|---|
| Registration hits duplicate detection (409) | Store `bevestigingsToken_<ID>_<rol>`, retry the same request with header `VR-BevestigingsToken`. The body must be identical: generate naam/IBAN/INSZ only on the first attempt. |
| Beheer detail / historiek | `?expectedSequence={{sequence}}`, retry on 412. |
| Before using another vereniging's projected data (e.g. naam for a lidmaatschap) | `wachtOp(rol)`: GET beheer detail of that vereniging with `expectedSequence`, retry on 412/404, store `naam<rol>`. |
| Zoeken, publiek detail (no sequence guard) | Generate a `ready` predicate from the expectation; retry until it holds, then run the real assertions once. |
| Every write | Store `VR-Sequence` from the response in `sequence`. |

Never `setTimeout`/sleep in a test script; always retry via `pm.execution.setNextRequest(pm.info.requestName)`.

## 5. Naming

- Feature prefix of 2-3 capitals per feature: `BR` bankrekeningnummers, `LO` locaties, `VT` vertegenwoordigers,
  `LM` lidmaatschappen, `ER` erkenningen, `CG` contactgegevens, `X` weigeringen.
- Collection: the feature name, e.g. `Bankrekeningnummers` (no prefix: the workspace already says regressie).
- Folder: `<ID> - <regel> -> <uitkomst>` (`BR2 - Zelfde IBAN (met/zonder spaties) -> gededupliceerd`).
- Request: `<ID> - <actie>` (`BR2 - Registreer authentieke vereniging (A)`, `BR2 - Beheer detail authentieke vereniging (A)`).
- Test: `<ID> <endpoint>: <verwachting>` (`BR2 beheer detail: 2 bankrekeningnummers`).
- Identifiers in code: English. Domain terms: Dutch (`vereniging`, `bankrekeningnummer`, `gededupliceerd`).

## 6. Scenario file format

A feature file exports data only; `postman/generate.js` turns every scenario into a folder:
registration of A → `stappen` → beheer detail → historiek → beheer zoeken / publiek detail / publiek zoeken
(only the endpoints present in `final`).

```js
// postman/features/<feature>/scenarios.js
module.exports = {
  name: 'Bankrekeningnummers',             // collection name
  description: '...',
  setup: SETUP_IBAN,                       // prerequest code of the first registration of every scenario (unique data)
  groepen: [{ name: 'Toevoegen', scenarios: [/* ... */] }],
};

// one scenario
{
  id: 'BR19',
  name: 'Zelfde IBAN opnieuw, ook met puntjes of spaties -> 400, IBAN is uniek',
  a: { bankrekeningnummers: [] },          // registration body of A (naam is added), or kbo: true
  registratie: { status: 400, ... },       // optional: expected result of the registration (default 202)
  stappen: [                               // writes after the registration, in order
    { naam: 'Voeg bankrekeningnummer A toe', actie: 'POST', pad: 'bankrekeningnummers',
      body: { bankrekeningnummer: { iban: '{{ibanA}}', doel: 'Lidgeld', titularissen: ['Frodo Baggins'] } } },
    { naam: 'Voeg zelfde IBAN met puntjes toe', actie: 'POST', pad: 'bankrekeningnummers', body: { /* ... */ },
      verwacht: { status: 400, detail: 'Het IBAN van een bankrekening moet uniek zijn binnen de vereniging.' } },
  ],
  final: { beheerDetail: { lijst: { veld: 'bankrekeningnummers', items: [{ bankrekeningnummerId: 1, iban: '{{ibanA}}' }] } } },
  historiek: { bevat: [{ gebeurtenis: 'BankrekeningnummerWerdToegevoegd', data: { bankrekeningnummerId: 1 }, aantal: 1 }] },
}
```

Building blocks (`shared/builders.js`):
- **Step** (`stappen[]`): `{ naam, actie, pad?, op? ('A'), vCode? (literal, e.g. an unknown vCode), body?, zonderToken?,
  verwacht?, bewaarId? }`.
  - `verwacht` (default `{ status: 202 }`) can also hold `detail`, `title` and
    `validatie: { veld, reden, code? }` (or an array). The veld is matched case-insensitively against the
    `validationErrors` keys, e.g. `bankrekeningnummer.Titularissen[0]`.
  - `bewaarId: 'x'` stores the id from the Location header in `{{x}}`, for ids you cannot know beforehand (reused
    verenigingen on Test).
  - `initiator: 'OVO000001'` sets `VR-Initiator` for that request (default from the root script / environment).
    Valid OVO codes: OVO000001, OVO002949, OVO002956, OVO003168. VLO (OVO000067) is refused for some actions.
  - Successful writes store `VR-Sequence` in `sequence`.
- **Final-state spec** per endpoint (subset match; `iban`/`insz` compared without spaces, dots or dashes; property
  names case-insensitive; arrays of objects matched per item):
  - `lijst: { veld, items }`: exactly these items.
  - `bevat`: at least these items.
  - `zonder`: none of these items.
  - `props` / `propsNiet`: properties that must (not) have this value.
  - `nietInResponse: [waarde]`: the value appears nowhere in the response. An IBAN is checked in every format.
- **Historiek**: `{ bevat: [{ gebeurtenis, data?, beschrijving?, aantal? }], geen: ['prefix'] }`.
  - `aantal` is the exact number of matching gebeurtenissen (default: at least one).
  - `geen: ['Bankrekeningnummer']` means no gebeurtenis starts with that prefix.
- `{{variables}}` in expectations are resolved at runtime.
- Small helpers that make a feature file readable (`voegToe`, `wijzig`, `rek`, `toegevoegd`, ...) live in the feature
  file. Move them to `shared/` only when a second feature needs them.
- Scenario ids must be unique within a feature; the generator fails otherwise.

## 7. Environments and running

The `Local` and `Test` environments live in the Postman workspace. Settings that differ between them:

| Setting | local | test |
|---|---|---|
| `kboModus` | `random` (Magda mock accepts any valid number) | `bestaand` (only real numbers; an existing vereniging is reused, so assert only what that rule guarantees) |
| `testdata_ipdcProductNummer` | `9` (wiremock) | `75395` |
| `superAdmin` | `true` | depends on the token; scenarios that need it are skipped when `false` |
| `maxRetries` / `retryDelayMs` | `10` / `800` | higher, because of parallel load |

Run a new feature:
1. `node postman/generate.js <feature>`
2. Import `postman/collections/<feature>.postman_collection.json` in the Postman workspace (once).
3. Run it in the Postman app with the `Local` environment, or with the CLI:
   `postman collection run <collection uid> -e <environment uid>`.

## 8. GitHub workflows

- `postman-feature.yml` (`workflow_dispatch` with a `choice` input `feature`, one option per feature, and
  `workflow_call` with the same input as a string; trigger: `gh workflow run postman-feature.yml -f feature=<feature>`):
  1. Look up the feature's collection UID in the `COLLECTIONS` map at the top of the workflow (rename-safe, unlike
     a lookup by name), install the Postman CLI and log in with `POSTMAN_API_KEY` (its owner needs workspace access).
  2. Run `postman collection run <collection uid> -e ${{ vars.POSTMAN_TEST_ENVIRONMENT_UID }} -r cli,junit,html`,
     overriding the Test values with `--env-var`: `beheer_url`, `publiek_url` from repository variables
     `POSTMAN_TEST_BEHEER_URL`, `POSTMAN_TEST_PUBLIEK_URL`, and `token_url`, `clientId`, `clientSecret`, `vr-api-key`
     from secrets `POSTMAN_TEST_TOKEN_URL`, `POSTMAN_TEST_CLIENT_ID`, `POSTMAN_TEST_CLIENT_SECRET`,
     `POSTMAN_TEST_VR_API_KEY`.
  3. Upload the reports as an artifact.
- `regressie-all.yml`:
  1. Run a `strategy.matrix.feature` over all features calling `postman-feature.yml`, with `fail-fast: false` and
     `max-parallel: 3`.
  2. A final job collects the junit files, publishes them, and sends one Slack message.
- GitHub only runs on Test.

## 9. New feature: checklist

1. Read the domain rules before writing scenarios: command handler, domain methods (`Throw<...>.If`), request
   validators, projections (which endpoints show what). List every rule and every exception.
2. Write `postman/features/<feature>/scenarios.js`: one scenario per rule (section 3.5), with a feature prefix.
   Start the file with the same "Startversie" comment as `features/bankrekeningnummers/scenarios.js`: after the
   import the collection is maintained in Postman and the file is not updated.
3. Extend `shared/builders.js` only generically if something can't be expressed.
4. Run `node postman/generate.js <feature>`, then run it locally until it's green.
5. Import the generated collection in the Postman workspace; from then on it is maintained there.
6. Add the feature to `COLLECTIONS` (with its collection UID) and `options` in `postman-feature.yml`, and to the matrix
   in `regressie-all.yml`. Commit the scenarios and the workflows, not the generated collection.

## 10. Migrating an existing collection

1. Inventory: for every request/folder in the old collection, note which rule it tests and which variables it uses
   from the environment.
2. Map variables:
   - Runtime state (`vCode2`, `sequence`, tokens) becomes collection variables set by the scenario.
   - Non-creatable references become `testdata_*`.
3. Check the domain code for rules the old collection does not cover, and add them.
4. Rewrite as scenarios in the new format. Don't convert scripts 1-to-1.
5. Run old and new side by side on Test. Remove the old folder after a few green runs.

## Don'ts

- Runtime variables in an environment; `pm.environment.set`.
- Branching on `pm.environment.name`.
- Hand-edited scripts in the generated collection or in the Postman app.
- Depending on folder order, on other scenarios, or on mutable existing data.
- Fixed sleeps instead of `expectedSequence` / ready-predicate retries.
- Real personal data in test data.
