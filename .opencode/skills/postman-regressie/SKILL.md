# Postman regressietests

One collection per feature, generated from a scenario file in the repo. The same collection runs locally (Postman app
or CLI) and on Test (GitHub). `postman/features/bankrekeningnummers/scenarios.js` is the reference implementation:
when in doubt, do what it does.

## 1. Architecture

**The Postman workspace is the source of truth.** Not everyone who works on the tests has the repo, so existing
collections are maintained in the Postman app and GitHub runs them from the workspace. The scenario files and
`generate.js` are only used to create the first version of a new feature's collection, which is then imported in the
workspace. Generated collection files are not committed (a daily sync from Postman to the repo for version control is
planned).

```
postman/
  shared/
    root-prerequest.js      token, VR-Initiator, VR-Api-Version, funcs (one source for every collection)
    helpers.js              test-script helpers: RETRY/retryIf, HELPERS (matches, getCI, resolve, norm)
    builders.js             request builders + endpoint checks (registreer, wachtOp, beheerDetail, historiek, ...)
  features/<feature>/
    scenarios.js            ONLY data: the scenarios of this feature
  generate.js               node postman/generate.js [feature]  ->  postman/collections/<feature>.postman_collection.json
  collections/              generated, not committed (import in the Postman workspace)
.github/workflows/
  postman-feature.yml       one feature: dropdown (workflow_dispatch) or reusable (workflow_call), input: feature
  regressie-all.yml         scheduled: matrix over all features -> postman-feature.yml, then projecties alone
```

- A feature file contains **data, not scripts**. Scripts are generated by the builders. If a scenario needs a check
  the builders can't express, extend the builders (generically), don't inline a one-off script.
- Every collection gets the same root pre-request script from `shared/root-prerequest.js`.
- The environments (`Local`, `Test`) live only in the Postman workspace, not in the repo.

## 2. Variables

| Kind | Where | Examples |
|---|---|---|
| Configuration | Postman environment (`Local`, `Test`) | `beheer_url`, `publiek_url`, `acm_url`, `token_url`, `maxRetries`, `retryDelayMs`, `kboModus`, `superAdmin` |
| Secrets | Postman Vault (`{{vault:test_clientSecret}}`), `--env-var` in GitHub. Local uses the committed docker-compose dev client directly. The publiek API key is always read from the vault secret `vr-api-key` (`--env-var "vr-api-key=..."` in GitHub) | `clientId`, `clientSecret`, `vr-api-key` |
| Fixed reference data that must exist on that environment | Postman environment, prefix `testdata_` | `testdata_ipdcProductNummer`, `testdata_kboNummer` |
| Runtime state | collection variables, set by scripts | `vCodeA`, `vCodeD`, `sequence`, `naamX`, `token`, `publiekApiKey`, `ibanA`, `inszFrodo` |

Rules:
- **If a script `set`s it, it never exists in an environment.** An environment variable wins over a collection
  variable when `{{x}}` is resolved, so a stale `vCodeA` or `sequence` in the environment silently breaks the run.
- Scripts use `pm.collectionVariables` for state. Never `pm.environment.set`.
- `testdata_*` is read-only: a test may reference it, never change it (parallel runs share it).
- Tests never branch on the environment name. Differences between local and Test are explicit settings
  (`kboModus: 'random' | 'bestaand'`, `superAdmin: true | false`, `testdata_ipdcProductNummer`, ...).
- Values specific to one scenario that must survive a retry get the scenario id in the key
  (`bevestigingsToken_<ID>_<rol>`, `naam_<ID>_<rol>`).

## 3. Scenario rules

1. **Self-contained.** A scenario registers every vereniging it needs (roles `A`, `D`, `X`, `Y`, `K`...) and stores
   the vCodes in `vCode<rol>`. It never depends on another folder or on existing data (except read-only `testdata_*`).
   Folders can run in any order and in parallel.
   The generator enforces this: the registration first unsets `vCode<rol>`. When the registration (or a `lees` step)
   fails, it sets `stop_<id>` and the folder script skips the rest of the scenario. So a failure shows up once, at its
   cause, and never as follow-up errors against the vereniging of a previous scenario.
2. **Unique data.** Namen contain the scenario id and a `{{$randomUUID}}`. IBANs are generated (valid Belgian IBAN).
   INSZ/KBO only where the API requires known numbers: then from `testdata_*` or the root script lists.
3. **Fictional persons:** Lord of the Rings names (Frodo Baggins, Samwise Gamgee, Aragorn Elessar, ...).
4. **Assert only on your own data.** Filter zoek results on your own vCode (`q=vCode:{{vCodeA}}`). Never count
   global results or assume "the latest" vereniging.
5. **One rule per scenario.** The name states the rule and the outcome: `Zelfde IBAN met spaties -> gededupliceerd`.
   Cover per rule: the happy path, every reason for rejection/niet-overnemen, boundaries (same day, open start/end,
   case/format differences), and "nothing to do" (no event).
6. **Check every endpoint where the data is visible**, with the projection-specific shape:
   beheer detail (with ids), historiek (gebeurtenis + data), beheer zoeken, publiek detail, publiek zoeken
   (no ids, no persoonsgegevens). Only generate requests for endpoints where the group is visible.
7. **Persoonsgegevens.** Where relevant, assert that INSZ/IBAN/titularissen do *not* appear where they must not
   (publiek endpoints, historiek of niet-overgenomen items). Use a "niet in response" check on the resolved value.
8. **Validation errors (400)** get their own scenarios: expected status + the problem details message
   (`pm.response.json().errors` / `detail`), not just the status.

## 4. Consistency and retries

Retry limits come from the environment (`maxRetries`, `retryDelayMs`); the root script waits when `loopCounter > 0`.

| Situation | Pattern |
|---|---|
| Registration hits duplicate detection (409) | Store `bevestigingsToken_<ID>_<rol>`, retry the same request with header `VR-BevestigingsToken`. The body must be identical: generate naam/IBAN/INSZ only on the first attempt. |
| Beheer detail / historiek | `?expectedSequence={{sequence}}`, retry on 412 and until the spec holds (`props`/`lijst`/`bevat`, every historiek `bevat`). A write can change A in the same transaction as another vereniging and return that one's `VR-Sequence` (markeer D als dubbel van A), so the sequence alone does not guarantee A is projected. |
| Before using another vereniging's projected data (e.g. naam for a lidmaatschap) | Step `{ wachtOp: 'X' }`: GET beheer detail of that vereniging with `expectedSequence`, retry on 412/404, store `naam<rol>`. |
| Zoeken, publiek detail, other projections (no sequence guard) | Generate a `ready` predicate from the expectation (`props`, `lijst`, `bevat` and `zonder`); retry until it holds, then run the real assertions once. |
| Asynchronous processing after a write (adresmatch of a locatie via a queue: its events come after the `VR-Sequence` of the write) | Beheer detail and historiek already wait until the spec holds. When a next step depends on the result, wait for it first: step `{ wachtOpGebeurtenis: { gebeurtenis, data } }`. Otherwise the outcome depends on timing (which of two identical locaties is removed, a write before or after the match). |
| Every write | Store `VR-Sequence` from the response in `sequence`. |

Never `setTimeout`/sleep in a test script; always retry via `pm.execution.setNextRequest(pm.info.requestName)`.

## 5. Naming

- Feature prefix of 2-3 capitals per feature: `BR` bankrekeningnummers, `LO` locaties, `VT` vertegenwoordigers,
  `LM` lidmaatschappen, `ER` erkenningen, `CG` contactgegevens, `ST` stopzetting, `SU` subverenigingen, `VW` verwijderen, `ZO` zoeken, `PR` projecties, `DD` dubbeldetectie, `GT` geotags,
  `X` weigeringen. A feature that spans several groups
  (dubbelmerge) uses the prefix of the group: `B` basisgegevens, `HA` hoofdactiviteiten, `WG` werkingsgebieden,
  `KBO` vereniging met rechtspersoonlijkheid, `ALL` all groups at once.
- Collection: the feature name, e.g. `Bankrekeningnummers` (no prefix: the workspace already says regressie).
- Folder: `<ID> - <regel> -> <uitkomst>` (`BR2 - Zelfde IBAN (met/zonder spaties) -> gededupliceerd`).
- Request: `<ID> - <actie>` (`BR2 - Registreer authentieke vereniging (A)`, `BR2 - Beheer detail authentieke vereniging (A)`).
- Test: `<ID> <endpoint>: <verwachting>` (`BR2 beheer detail: 2 bankrekeningnummers`).
- Identifiers in code: English. Domain terms: Dutch (`vereniging`, `bankrekeningnummer`, `gededupliceerd`).

## 6. Scenario file format

A feature file exports data only; `postman/generate.js` turns every scenario into a folder:
registration of A → `stappen` → beheer detail → historiek → beheer zoeken / publiek detail / publiek zoeken
(only the endpoints present in `final`).

```js
// postman/features/<feature>/scenarios.js
module.exports = {
  name: 'Bankrekeningnummers',             // collection name
  description: '...',
  setup: SETUP_IBAN,                       // prerequest code of the first registration of every scenario (unique data)
  groepen: [{ name: 'Toevoegen', scenarios: [/* ... */] }],
};

// one scenario
{
  id: 'BR19',
  name: 'Zelfde IBAN opnieuw, ook met puntjes of spaties -> 400, IBAN is uniek',
  a: { bankrekeningnummers: [] },          // registration body of A (naam is added), or kbo: true
  registratie: { status: 400, ... },       // optional: expected result of the registration (default 202)
  stappen: [                               // writes after the registration, in order
    { naam: 'Voeg bankrekeningnummer A toe', actie: 'POST', pad: 'bankrekeningnummers',
      body: { bankrekeningnummer: { iban: '{{ibanA}}', doel: 'Lidgeld', titularissen: ['Frodo Baggins'] } } },
    { naam: 'Voeg zelfde IBAN met puntjes toe', actie: 'POST', pad: 'bankrekeningnummers', body: { /* ... */ },
      verwacht: { status: 400, detail: 'Het IBAN van een bankrekening moet uniek zijn binnen de vereniging.' } },
  ],
  final: { beheerDetail: { lijst: { veld: 'bankrekeningnummers', items: [{ bankrekeningnummerId: 1, iban: '{{ibanA}}' }] } } },
  historiek: { bevat: [{ gebeurtenis: 'BankrekeningnummerWerdToegevoegd', data: { bankrekeningnummerId: 1 }, aantal: 1 }] },
}
```

Building blocks (`shared/builders.js`):
- **Step** (`stappen[]`): `{ naam, actie, pad?, op? ('A'), vCode? (literal, e.g. an unknown vCode), body?, zonderToken?,
  verwacht?, bewaarId? }`.
  - `verwacht` (default `{ status: 202 }`) can also hold `detail`, `title` and
    `validatie: { veld, reden, code? }` (or an array). The veld is matched case-insensitively against the
    `validationErrors` keys, e.g. `bankrekeningnummer.Titularissen[0]`.
  - `bewaarId: 'x'` stores the id from the Location header in `{{x}}`, for ids you cannot know beforehand (reused
    verenigingen on Test).
  - `initiator: 'OVO000001'` sets `VR-Initiator` for that request (default from the root script / environment).
    Valid OVO codes: OVO000001, OVO002949, OVO002956, OVO003168. VLO (OVO000067) is refused for some actions.
  - `url: 'kbo'` replaces `{vCode}/{pad}` (path after `/v1/verenigingen/`), e.g. a refused registration as a step.
  - `headers: { 'If-Match': '{{etag1}}' }` adds request headers (`null` removes a header the root script sets, e.g.
    `{ 'X-Correlation-Id': null }`); `bewaarHeader: { ETag: 'etag1' }` stores response
    headers of a successful write; `bewaarVeld: { bevestigingsToken: 'token_DD1' }` stores a property of the JSON
    response root, whatever the status (the bevestigingstoken of a 409).
  - `verwacht.status` may be an array (`[200, 202]`) when the start state is unknown (reused vereniging);
    `verwacht.locatie: '{{vCodeA}}'` checks the last segment of the Location header.
  - `verwacht.inResponse` / `verwacht.nietInResponse: ['{{vCodeA}}']`: values that must (not) appear in the response
    body. With `herhaal: true` the step is retried until status, `inResponse` and `nietInResponse` hold: for an outcome
    of an eventually consistent projection, e.g. dubbeldetectie (409 with / without A after stopping A).
  - `{ naam, lees: { veld, match, bewaar: { contactgegevenId: 'kboEmailId' }, optioneel? } }` reads beheer detail and
    stores properties of the one matching item (data from KBO, ids on a reused vereniging), retried until exactly one
    item matches (a value set asynchronously). With `optioneel` the variables are unset when nothing matches;
    `alleenAls: 'kboEmailId'` on a step skips it when the variable is empty. With `eerste: true` at least one item
    must match and the first one (lowest id) is stored, e.g. one of the vertegenwoordigers from KBO (`match: { bron: 'KBO' }`).
  - `{ naam, wachtOpGebeurtenis: { gebeurtenis, data? } }` waits until A's historiek contains that gebeurtenis (subset
    match on data), e.g. `AdresWerdOvergenomenUitAdressenregister` with `{ locatieId: 1 }` before the next step depends
    on the adresmatch. The scenario stops when it does not appear.
  - `actie: 'GET'` with `beheerPad: 'v1/projections/...'` (path after `{{beheer_url}}/`) for a status check on an
    endpoint outside `/v1/verenigingen` (401 without token, 404 without parameter).
  - `api: 'publiek' | 'acm' | 'beheer'` with `apiPad` sends the step to that API (publiek gets the API key). With
    `herhaal` and `verwacht.inResponse` it waits until a projection without sequence guard shows the vereniging, e.g.
    before a step that should remove it: otherwise an `afwezig` check also passes when that projection lags behind.
    Look for a value that is not in the request (the naam, not the vCode of a `q=vCode:` search).
  - Successful writes store `VR-Sequence` in `sequence`. A successful registration stores the naam in `naam<rol>`
    and its own `VR-Sequence` in `sequence<rol>` (e.g. `mutaties?sinds={{sequenceA}}`: everything after the registration).
  - `op: 'D'` sends the step to another vereniging of the scenario (`{{vCodeD}}`).
  - `{ wachtOp: 'X' }` waits until vereniging X is in beheer detail and stores its naam in `naamX` (also for a KBO
    vereniging), e.g. before a lidmaatschap refers to it.
- **Scenario options**: `geenRegistratie: true` (no vereniging A: only refused requests), `vereist: { kboModus:
  'bestaand' }` (skipped on other environments; the skip is visible as one passing test `<id> overgeslagen: draait
  enkel op Test (kboModus = bestaand) (deze environment: ...)`, the folder description says where it runs, and the
  collection description and the output of `generate.js` list every scenario that does not run everywhere. In the
  Postman app a skipped request itself shows as "Request could not be sent". Use only the existing settings
  `kboModus` and `superAdmin`; add a readable text for a new value to `VEREIST_UITLEG` in `builders.js`), `controles: [{ naam, api: 'beheer' | 'publiek' | 'acm', pad, spec }]`
  (GET on another endpoint, retried until the spec holds on the JSON root, e.g. ACM `v1/verenigingen?insz=...` with
  `bevatOp('verenigingen', [...])`; `acm` uses `acm_url` from the environment), `kbo: true` or `kbo: 'testdata_kboNummersMetEmail'` (pick from that
  list; such a vereniging is reused, also locally), `zoeken: [{ api: 'publiek', q, gevonden }]` (extra searches),
  `verenigingen: { D: { korteNaam: '...' }, X: {}, K: { kbo: true } }` (extra verenigingen, registered after A in this
  order and before the `stappen`; vCode in `vCode<rol>`, naam in `naam<rol>`; a failed registration stops the scenario;
  several KBO verenigingen in one scenario always get different numbers, also with `kboModus: 'bestaand'`),
  `registratieUrl: 'vzer'` (register A via that path after `/v1/verenigingen/` instead of `{{registreerVereniging}}`),
  `controles: [{ naam, pad, spec, publiek? }]` (GET `{{beheer_url}}/<pad>` after the other checks, retried until the
  JSON root satisfies the spec, e.g. the locatie lookup: `{ pad: 'v1/projections/admin/locaties/gekoppeldmetgrar/vCode/{{vCodeA}}',
  spec: lijstOp('data', [{ locatieId: 1, adresId: '2208355' }]) }`). A controle can set request headers after the root
  script: `headers: { 'VR-Api-Version': null }` (`null` removes the header, e.g. to check the response without v2).
  With `body` the controle is a POST with that JSON body, e.g. ACM `{ api: 'acm', pad: 'v1/verenigingen', body: { insz: '{{inszFrodo}}' } }`.
- **Final-state spec** per endpoint (subset match; `iban`/`insz` compared without spaces, dots or dashes; property
  names case-insensitive; arrays of objects matched per item; a `{{variable}}` string matches the same number):
  - `lijst: { veld, items, inVolgorde? }`: exactly these items (`inVolgorde`: also in this order). `lijst`, `bevat` and
    `zonder` can also be an array, one per veld, to check several groups on one endpoint.
  - `afwezig: true` (publiek detail / zoeken): the vereniging is not found (retried until it is gone).
  - `bevat`: at least these items.
  - `zonder`: none of these items.
  - `props` / `propsNiet`: properties that must (not) have this value.
  - `nietInResponse: [waarde]`: the value appears nowhere in the response. An IBAN is checked in every format.
  - `telling: [{ veld, aantal, waar?: { code: '^BE2\\d{8}$' }, naam? }]`: exactly `aantal` items in `veld` (only those
    whose properties match the `waar` regexes), e.g. the number of gemeenten in the werkingsgebieden parameter-API.
  - `minstens: { veld, waarde }`: every value of `veld` (an object or a list) is a number `>= waarde`, waited for, e.g.
    the projection status: `{ veld: 'status', waarde: '{{sequence}}' }` (every projection processed the last write).
  - `veld: ''` is the JSON root itself, for a response that is a list (the mutatiedienst: `bevatOp('', [{ vCode }])`).
- **Historiek**: `{ bevat: [{ gebeurtenis, data?, beschrijving?, aantal?, naam?, nietIn? }], geen: ['prefix'] }`.
  - `aantal` is the exact number of matching gebeurtenissen (default: at least one).
  - `geen: ['Bankrekeningnummer']` means no gebeurtenis starts with that prefix.
  - `totaal: 1`: the exact number of gebeurtenissen in the historiek (verwijderen clears it to the deletion only).
  - `naam`: the test title instead of the (large) data, e.g. one entry per group of the samenvoegingsevent.
  - `nietIn: ['{{ibanA}}', '{{inszFrodo}}']`: persoonsgegevens that must not appear in the matching gebeurtenissen.
- `{{variables}}` in expectations are resolved at runtime.
- Small helpers that make a feature file readable (`voegToe`, `wijzig`, `rek`, `toegevoegd`, ...) live in the feature
  file. Move them to `shared/` only when a second feature needs them.
- Scenario ids must be unique within a feature; the generator fails otherwise.

## 7. Environments and running

The `Local` and `Test` environments live in the Postman workspace. Settings that differ between them:

| Setting | local | test |
|---|---|---|
| `kboModus` | `random` (Magda mock accepts any valid KBO number and INSZ) | `bestaand` (only real numbers; an existing vereniging is reused, so assert only what that rule guarantees; KSZ only knows the INSZ in the feature lists) |
| `testdata_ipdcProductNummer` | `9` (wiremock) | `75395` |
| `testdata_ipdcProductNummer2` (a second, different product) | `10062` (wiremock) | `10062` |
| `testdata_kboNummersMetEmail` | `0468831484` (wiremock: must be in the regex of `wiremock/mappings/GeefOnderneming.json`, other numbers get `fallback.xml` without contactgegevens) | `0409724634,0407622110` |
| `testdata_kboNummerOnbekend`, `...GeenVereniging`, `...Vestiging`, `...Stopgezet` | not needed (scenario skipped) | `0000000196`, `0462925669`, `2289324120`, `0476660176` |
| `testdata_inszOverleden` (KSZ: overleden) | `03010112343,99010112390` (wiremock `GeefPersoon.01234567890.json`) | `21030941172,04071007648,12071022468,20030708054,99040713120,09031929128,48080805986` |
| `testdata_inszNietGekend` (KSZ: niet gekend) | not needed (the Magda mock knows every valid INSZ; scenario skipped with `vereist: { kboModus: 'bestaand' }`) | `62110181549,78090770807,37082540962,05111699268,08012047075,56041985273,81092483218` |
| `superAdmin` | `true` | depends on the token; scenarios that need it are skipped when `false` |
| `maxRetries` / `retryDelayMs` | `10` / `800` | higher, because of parallel load |

**Adressenregister (GRAR).** Locaties are matched against the real adressenregister on Test, and locally too when the
Admin API is configured with a real GRAR. The wiremock GRAR (`appsettings.development.json`) only knows
Affligem/1790, Hekelgem/1790, Dendermonde/9200 and Destelbergen, ignores the street, and returns other results than the
real one (Hekelgem: match vs. niet uniek). Use addresses whose result is the same everywhere you run, and check each
one on the real register before relying on it:

| Address / adresId | Result |
|---|---|
| Fosselstraat 48, 1790 Affligem (also `0048`, lowercase) | gevonden, adresId 2208355 |
| Dreef 21, 1740 Ternat | gevonden, adresId 667831 |
| Fosselstraat 48 bus B, 1790 Affligem; Prieelstraat 12 bus 10, 1740 Ternat | niet uniek |
| An invented gemeente (Hobbitsteeg 1, 9999 Hobbitstee) | niet gevonden: use this for every locatie where the match does not matter |
| adresId 9999999 / 320702 / 3213019 | 400: kon niet gevalideerd worden / verwijderd / niet meer actief |

An existing street in an existing gemeente can be matched (and its adres replaced) on the real register, which makes
assertions on that locatie flaky. The locatie lookup (`/v1/projections/admin/locaties/gekoppeldmetgrar/...`) and
deleting a vereniging need a superAdmin token (`vereist: { superAdmin: true }`).

**NUTS/LAU table (local).** Werkingsgebieden on gemeente level and the gemeente/provincie geotags come from the
`PostalNutsLauInfo` table. Test fills it via the AddressSync; locally it is empty until you fill it once (superAdmin
token, takes a few minutes, reads all postcodes from the GRAR): `POST {{beheer_url}}/v1/admin/syncnutslauinfo`.
Without it, a gemeente as werkingsgebied gives "Het opgegeven werkingsgebied is niet gekend" and a geotag search on a
gemeente or provincie finds nothing (only the postcode of a locatie is a geotag).

Run a new feature:
1. `node postman/generate.js <feature>`
2. Run it locally from the file until it is green (no Postman login needed; the publiek API does not check the key
   locally), whole or one folder:
   `postman collection run postman/collections/<feature>.postman_collection.json -e postman/environments/local.json --env-var "vr-api-key=lokaal" [-i "<folder name>"]`
3. Import `postman/collections/<feature>.postman_collection.json` in the Postman workspace (once).
4. Run it in the Postman app with the `Local` environment, or with the CLI:
   `postman collection run <collection uid> -e <environment uid>`.

Probing the API by hand with curl from Git Bash: write non-ASCII characters as JSON escapes (`België`).
Arguments reach curl in the Windows codepage, so `België` arrives as invalid UTF-8 and the API answers 500.

## 8. GitHub workflows

- `postman-feature.yml` (`workflow_dispatch` with a `choice` input `feature`, one option per feature, and
  `workflow_call` with the same input as a string; trigger: `gh workflow run postman-feature.yml -f feature=<feature>`):
  1. Look up the feature's collection UID in the `COLLECTIONS` map at the top of the workflow (rename-safe, unlike
     a lookup by name), install the Postman CLI and log in with `POSTMAN_API_KEY` (its owner needs workspace access).
  2. Run `postman collection run <collection uid> -e ${{ vars.POSTMAN_TEST_ENVIRONMENT_UID }} -r cli,junit,html`,
     overriding the Test values with `--env-var`: `beheer_url`, `publiek_url` from repository variables
     `POSTMAN_TEST_BEHEER_URL`, `POSTMAN_TEST_PUBLIEK_URL`, and `token_url`, `clientId`, `clientSecret`, `vr-api-key`
     from secrets `POSTMAN_TEST_TOKEN_URL`, `POSTMAN_TEST_CLIENT_ID`, `POSTMAN_TEST_CLIENT_SECRET`,
     `POSTMAN_TEST_VR_API_KEY`.
  3. Upload the reports as an artifact.
- `regressie-all.yml` (scheduled Monday and Wednesday 02:00 UTC, and `workflow_dispatch` with input `max_parallel`,
  default 3; trigger: `gh workflow run regressie-all.yml [-f max_parallel=5]`; one run at a time via `concurrency`):
  1. A first job reads the features from the keys of `COLLECTIONS` in `postman-feature.yml` (no separate list).
  2. Run a `strategy.matrix.feature` over those features calling `postman-feature.yml`, with `fail-fast: false` and
     `max-parallel: max_parallel`.
  3. Features that check the whole system run alone after the others (`LAST` in the workflow: `projecties`, every
     projection caught up with the last write): with other features writing in parallel the projections lag behind.
  4. A final job collects the junit files, publishes them (`dorny/test-reporter`), and sends one Slack message with the
     result per feature (`secrets.SLACK_WEBHOOK_URL`).
- GitHub only runs on Test.

## 9. New feature: checklist

1. Read the domain rules before writing scenarios: command handler, domain methods (`Throw<...>.If`), request
   validators, projections (which endpoints show what). List every rule and every exception.
2. Write `postman/features/<feature>/scenarios.js`: one scenario per rule (section 3.5), with a feature prefix.
   Start the file with the same "Startversie" comment as `features/bankrekeningnummers/scenarios.js`: after the
   import the collection is maintained in Postman and the file is not updated.
3. Extend `shared/builders.js` only generically if something can't be expressed.
4. Run `node postman/generate.js <feature>`, then run it locally until it's green.
5. Import the generated collection in the Postman workspace; from then on it is maintained there.
   Report to the user, as explicit action items at the top: every environment variable the collection needs that is
   not yet in the workspace environments (name and value per environment; compare with `environments/local.json` and
   `test.json`), and the list `generate.js` prints of scenarios that only run on Local, on Test or with a superadmin
   token. Never add a new environment variable just to skip scenarios.
6. Add the feature to `COLLECTIONS` (with its collection UID) and `options` in `postman-feature.yml`;
   `regressie-all.yml` picks it up from `COLLECTIONS`. Commit the scenarios and the workflows, not the generated
   collection.

## 10. Migrating an existing collection

1. Inventory: for every request/folder in the old collection, note which rule it tests and which variables it uses
   from the environment.
2. Map variables:
   - Runtime state (`vCode2`, `sequence`, tokens) becomes collection variables set by the scenario.
   - Non-creatable references become `testdata_*`.
3. Check the domain code for rules the old collection does not cover, and add them.
4. Rewrite as scenarios in the new format. Don't convert scripts 1-to-1.
5. Run old and new side by side on Test. Remove the old folder after a few green runs.

## Don'ts

- Runtime variables in an environment; `pm.environment.set`.
- Branching on `pm.environment.name`.
- Hand-edited scripts in the generated collection or in the Postman app.
- Depending on folder order, on other scenarios, or on mutable existing data.
- Fixed sleeps instead of `expectedSequence` / ready-predicate retries.
- Real personal data in test data.
- New environment variables to gate scenarios (`vereist: { nieuweVariabele: ... }`): a missing variable silently
  skips the scenario in the workspace.
